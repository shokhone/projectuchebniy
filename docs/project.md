# Выбор темы проекта и обоснование модели проектирования

## Тема проекта
**«Разработка информационной системы “Электронная карта пациента” для автоматизации процессов медицинской организации»**

## Обоснование модели проектирования

Для реализации проекта выбрана **гибкая методология (Agile)**.

### Причины выбора

Проект характеризуется высокой степенью неопределенности требований на старте и необходимостью тесного взаимодействия с конечными пользователями. Выбор Agile-подхода обусловлен следующими факторами:

#### 1. Модульная структура системы
Система состоит из логически независимых модулей:
- Регистратура (ввод карточек пациентов)
- Запись на приём (управление расписанием)
- Ведение медицинских записей (диагнозы, назначения)
- Выписка и больничные листы
- Отчётность и аналитика

Agile-подход позволяет организовать разработку как последовательную реализацию модулей с возможностью изменения приоритетов. Каждый модуль может быть проработан, протестирован и передан в опытную эксплуатацию независимо от остальных.

#### 2. Высокая потребность в обратной связи
Ключевые пользователи системы — врачи, регистраторы и администраторы. После знакомства с промежуточными версиями системы у них возникают уточнения:
- форматы выписных эпикризов;
- набор полей электронной карты;
- правила валидации и проверки вводимых данных.

Agile предполагает регулярные демонстрации работающего функционала и сбор обратной связи, что позволяет адаптировать систему под реальные рабочие процессы, а не под изначально зафиксированные предположения.

#### 3. Гибкость к изменениям требований
В медицинской среде требования подвержены изменениям:
- изменение форм отчётности для надзорных органов;
- обновление классификаторов (МКБ-10/МКБ-11);
- уточнение业务流程 в зависимости от специфики организации;
- добавление новых типов медицинских документов.

Гибкая методология позволяет реагировать на эти изменения без пересмотра всего плана работ. Изменения интегрируются в процесс разработки по мере их появления, а не накапливаются до этапа приёмки.

#### 4. Снижение рисков
В отличие от каскадного подхода, где интеграция всех компонентов происходит в конце проекта, Agile предполагает:
- непрерывное тестирование на реальных сценариях;
- раннее выявление несоответствий между ожиданиями пользователей и реализованным функционалом;
- возможность скорректировать направление разработки с минимальными затратами.

Система получает прирост функциональности постепенно, что позволяет контролировать качество на каждом этапе и исключить ситуацию «большого взрыва» при финальной интеграции.

### Сравнение с альтернативными моделями

В качестве альтернативы рассматривалась **каскадная (Waterfall) модель**. Отказ от неё обоснован следующим:

| Критерий | Agile | Каскадная модель (Waterfall) |
| :--- | :--- | :--- |
| **Изменение требований** | Интегрируются в процессе разработки | Требуют формального пересмотра документации и сроков |
| **Интеграция модулей** | Поэтапная интеграция и тестирование | Риск «узкого места» при интеграции всех модулей в конце проекта |
| **Форматы документов** | Уточняются и валидируются пользователями в процессе | Жёсткая фиксация на этапе технического задания, сложность доработок |
| **Демонстрация результатов** | Регулярные демонстрации работающего функционала | Результат виден только на финальном этапе |
| **Предсказуемость сроков** | Гибкое планирование с возможностью корректировки | Чёткое, но жёсткое планирование |

Каскадная модель не обеспечивает необходимой гибкости при изменении требований к медицинским документам и отчётности, что делает её неприменимой для данного проекта.

### Практическая организация Agile-процесса

В рамках проекта планируется реализовать следующие практики гибкой разработки:

| Практика | Описание |
| :--- | :--- |
| **Итерационная разработка** | Разработка ведётся короткими циклами (2–3 недели), в конце каждого цикла предоставляется работающий прирост функциональности |
| **Регулярные демонстрации** | В конце каждой итерации проводится демонстрация результатов с участием врачей и регистраторов для сбора обратной связи |
| **Приоритизация требований** | Бэклог требований ведётся в GitHub Projects, приоритеты пересматриваются на основе текущих потребностей медицинской организации |
| **Непрерывное тестирование** | Тестирование проводится на протяжении всей разработки, включая проверку корректности формирования медицинских документов |
| **Прозрачность процесса** | Ведётся открытая доска задач, доступная всем участникам проекта для отслеживания текущего статуса работ |

Такой подход позволяет обеспечить высокое качество конечного продукта при сохранении гибкости и способности адаптироваться к изменениям на любом этапе разработки.
